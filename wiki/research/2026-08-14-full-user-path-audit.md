# 2026-08-14 全链路用户路径审计

## 结论

产品方向本身是“用户对话 → Agent 理解与研究 → 网页/小程序返回可比较的吃住行玩方案”。此前实现偏移并非一个按钮错误，而是语义门控、数据接线、状态持久化和前端承诺同时把内部工程结构置于用户任务之前。

## 发现与纠正

| 偏移 | 用户影响 | 当前纠正 |
| --- | --- | --- |
| 用正则判断出发/抵达信息是否齐全 | “广州，飞机”等补充被拦截或重复追问 | Parent Agent 结合完整历史理解；目的地明确即保存，缺少出发地不阻塞目的地内研究。 |
| Capability Registry 与 Planner 用字符串包含关系猜意图 | Skill/Workflow 表面存在，实际会因措辞变化走错 | Registry 只校验显式 capability ID，Planner 只编排父 Agent 给出的 `focusOrder`。 |
| 程序把第一个住宿候选当位置锚点并预选 | 高德排序被冒充为 Agent 决策 | 所有候选初始未确认；用户在方案区选择后才提交。 |
| “和父母同行”保存了关系却默认一人 | 预算、住宿和节奏全链路失真 | 首次写入有明确同行关系却漏掉可推断人数时拒绝落库，模型根据原话修正。 |
| Web 与小程序曾以手工行程/列表为主 | 用户必须先做完 Agent 本应完成的工作 | Web、微信与支付宝入口统一为 Chat-first，方案和地图是 Agent 输出面。 |
| 前端展示 Provider、Smoke、revision 等内部状态 | 普通用户无法理解，也无法恢复 | 界面只说明旅行要求、实时资料、影响和恢复动作；内部合同仅留服务端。 |
| 高德结果没有照片和内嵌地图 | 用户无法判断地点和空间关系 | POI 请求包含照片；静态地图由服务端代理，前端只接收图片。 |
| `TRAVEL_AGENT_DATA_DIR` 只作用于行程，不作用于对话 | 重启或切换目录后对话与行程断链 | 对话与行程使用同一配置根；数据库配置也同时作用于两类 repository。 |
| 测试/文档把 fixture、Schema 和页面加载写成“完成” | 交付声明高于真实能力 | 状态文档区分合同测试、真实模型、真实浏览器和真实外部数据四种证据。 |

## 用户级验收证据

- 真实模型：DeepSeek `deepseek-v4-pro` 两轮调用通过，保存大理、5 天、3 人、广州、飞机，并继续发起联动研究。
- 真实浏览器：桌面与 390×844 手机视口完成登录、首次自然语言咨询、简短补充、失败恢复和状态核对。
- 外部数据：当前无 `AMAP_API_KEY`，因此真实地点、照片和地图仍未验收；产品明确显示不可用，不生成替代候选。
- 自动化：完整 `npm run check` 覆盖 Runtime、HTTP、MCP、对话、存储、地图合同、Web 构建与两种小程序工程。

## 仍需外部条件

高德 Web 服务 Key、有效 Kimi 视觉账户、飞猪/铁路/酒店授权、社交平台合规只读账号和生产登录主体都必须由账号持有者配置。获得任一条件后，都要沿真实用户路径验证，而不是只运行 Provider 单接口 smoke。
