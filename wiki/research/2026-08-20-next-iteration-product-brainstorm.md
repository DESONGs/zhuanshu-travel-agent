## 一句话结论

Travel Agent 不应该成为另一个携程、飞猪、高德或小红书，也不应该只做一个能生成行程文字的聊天机器人。

更合适的产品定义是：

> **把散落在小红书、抖音、微信、高德和 OTA 里的旅行信息，变成一条适合这群人、能在地图上看懂、可以继续执行的旅行路线。**

这里每一类能力各自负责不同的事情：

- 小红书、抖音和微信帮助发现当地人、小众旅行者和真实到访者提到的地方。
- 高德帮助确认地点、位置、距离、路线、入口和已有的设施资料。
- 飞猪、途牛等 OTA 帮助确认酒店、航班、铁路、价格、库存和预订入口。
- Travel Agent 不复制这些平台，而是判断“它是否适合这次旅行”，再把吃、住、行、玩连成一趟完整旅行。
- Web、iOS、Android、微信、支付宝和 MCP 让同一趟旅行可以从不同入口开始和继续，而不是各做一套互不相通的产品。

## 本次修正：第 5、6、7 项全部保留

上一轮判断把全平台、登录/MCP、社交内容渠道更多地看成了成本。本次修正后，三者都应保留，因为它们分别解决中国旅行产品非常现实的三个问题。

### 1. 全平台为什么要保留

旅行天然会跨设备：

- 出发前，用户可能在电脑上比较路线、酒店和预算。
- 旅途中，用户主要使用手机查看地图、下一站和临时调整。
- 国内用户可能更愿意从微信或支付宝进入，不想额外安装 App。
- iOS、Android 用户需要更稳定的相机、语音、通知和定位体验。

因此，全平台不是为了证明技术能力，而是为了让一趟旅行在不同场景中不断档。

需要避免的不是“支持全平台”，而是每个平台各写一套旅行逻辑。正确方式是一套旅行服务和状态，多种适合各自设备的界面：

- 桌面端适合对话、比较、地图和完整路线一起看。
- 移动端适合“现在做什么、怎么去、下一步是什么”。
- 小程序适合低门槛开始、分享和旅途中快速打开。
- 原生 App 适合语音、图片、通知、定位和长期使用。

### 2. 登录、MCP 与对外能力为什么要保留

登录的价值不是多几个按钮，而是让用户在手机、电脑、小程序和 App 之间继续同一趟旅行。

- 微信、支付宝是国内用户的重要入口。
- Google、Apple 是入境游客和海外用户熟悉的入口。
- 不同入口登录后，应回到同一个旅行账号和同一份行程，而不是生成多个孤立账号。

登录时机仍应尽量靠后：用户可以先描述需求、看到 Agent 的理解；当需要保存、跨端继续、分享或跳转预订时再完成登录。这样既保留账号体系，也不让登录阻断第一次价值体验。

MCP 和可复用接口也应保留。它们不是单独再做一款产品，而是让用户在其他 AI 助手中也能调用同一套旅行能力。例如，用户在 Codex、WorkBuddy 或其他助手里讨论假期时，可以把旅行要求交给 Travel Agent，并在网页或手机上继续。这可能成为比单独购买流量更低成本的分发渠道。

### 3. 小红书、抖音和微信为什么要保留

在中国旅行场景中，这些渠道不是普通的“内容补充”，而是发现长尾美食、小众体验、近期排队情况和真实踩坑的重要入口。

但它们适合做“发现线索”，不适合单独充当事实来源：

- 一篇笔记可以告诉我们某个菜、路线或体验值得继续调查。
- 地点是否存在、是否营业、在哪里、怎么去，应再由地图、官方资料或电话等来源核验。
- 酒店房态、票价和库存，应由 OTA 或官方渠道核验。
- 高度雷同、同源转载、推广和互相抹黑的内容，不能用数量直接形成结论。

接入顺序不必一开始就依赖大规模自动搜索：

1. 先支持用户粘贴小红书、抖音和微信分享链接，由 Agent 提炼地点、菜品、排队、季节和风险。
2. 建立少量经过运营核验的目的地资料，保证没有社交账号时仍有基础质量。
3. 使用旅行结束后的结构化到访反馈补充“实际花费、等待、是否值得、信息是否变化”。
4. 在平台条款、账号和安全隔离满足后，再启用受限的只读搜索。

这种顺序保留了国内内容渠道的价值，也避免整个产品被一个容易风控或变化的平台接口卡住。

## 从旅行者角度重新梳理产品

### 用户真正想买的不是信息，而是少操心

用户已经可以在不同平台找到很多信息。真正耗时间的是：

- 不知道哪些内容是推广，哪些真的适合自己。
- 同行人的预算、体力、儿童、长辈、饮食和兴趣互相冲突。
- 酒店看起来很好，但每天去景点要绕很久。
- 找到了小众餐厅，却不知道是否需要预约、怎么点菜、外国人是否方便使用。
- 航班、酒店、天气或营业状态变化后，又要重新做一遍攻略。

所以 Travel Agent 的核心工作不是“再给十个结果”，而是完成五个动作：

1. **找到**：从社交内容、地图、OTA 和用户提供的资料里找到线索。
2. **核实**：区分体验分享、稳定事实和实时价格，不把模型印象当成资料。
3. **判断**：说明为什么适合这次旅行和这些同行人。
4. **串起来**：把地点、住宿、交通、时间和预算放到同一张地图和同一条路线里。
5. **跟着变**：下雨、闭店或延误时，只调整受影响的部分。

### 产品不再围绕“四个模块”组织

吃、住、行、玩仍然必须完整，但用户不应该逐个完成四次搜索。

更自然的结果是：

- Agent 先给一份主推荐路线。
- 只把真正影响结果的两三个选择交给用户，例如“住古城更方便，还是住洱海边更安静”。
- 用户选择后，吃、住、行、玩一起调整。
- 所有候选都放回地图和日程中判断，而不是停留在独立卡片里。

## 下一迭代的产品形态

### 1. 首屏：先得到帮助，不先学习产品

用户可以通过文字、语音或简单选择器开始：

- “国庆带父母去大理五天，少走路，想吃本地菜。”
- “还没决定去哪，三天，不想做攻略。”
- 粘贴一组小红书、抖音或微信链接，让 Agent 帮忙整理。

选择器只补充最常见的方向，例如预算、节奏、同行人和最在意的体验；它不取代自然语言，也不让用户填写复杂表格。

### 2. 第一次结果：一份主方案，而不是一屏候选

第一次结果优先显示：

- 一句话说明 Agent 如何理解这趟旅行。
- 一张包含住宿锚点、重点地点和主要路线的地图。
- 一份主推荐方案。
- 两到三个需要用户决定的关键取舍。
- 目前缺少或仍需核验的信息。

地点图片、完整设施、全部报价和来源细节在用户展开后再出现。

### 3. 地图：成为整趟旅行的共同语言

地图不只是显示地点，而是帮助用户回答：

- 这些地方是否在同一条动线上？
- 从酒店过去要多久，要走多少路？
- 父母、儿童或行动不便的同行人是否会太累？
- 哪个选择虽然热门，但会导致明显绕路？
- 机场或车站到酒店，再到第一顿饭，能否顺畅衔接？

导航仍跳转高德，不在 Travel Agent 内重做导航系统。

### 4. 详情：只在需要判断时展开

用户点开一个地点时，再显示：

- 实景图和地图位置；
- 为什么适合这次旅行；
- 当地特色和推荐体验；
- 排队、预约、点菜、支付、语言和过敏提示；
- 卫生间、电梯、坡道、储物柜等已有资料；
- 信息来源和核验时间；
- 到访者反馈中有帮助的结构化信息。

设施存在不等于当前正常运行，界面继续明确标注“非实时、建议现场确认”。

### 5. 行中：从“行程文档”变成当天助手

旅途中移动端优先显示：

- 现在要去哪里；
- 推荐怎样过去；
- 下一项是否受到天气、营业或延误影响；
- 需要预约、取票或准备什么；
- 如果临时不去，最合适的备选是什么。

这会让用户在生成行程以后仍然继续使用产品。

### 6. 行后：点评首先帮助下一位旅行者

用户不需要写长篇游记，只需回答少量有帮助的问题：

- 值不值得；
- 实际花费和等待；
- 是否适合长辈、儿童或入境游客；
- 现场信息有没有变化；
- 哪一种旅行者可能更喜欢这里。

反馈先服务于下一次推荐，不建设关注、点赞和内容 Feed。

## 国内与入境用户不必二选一

两类用户可以共用同一个产品内核，但入口表达和重点不同。

### 国内用户看到的价值

> 不用在小红书、高德和 OTA 之间来回切换，直接得到一条适合同行人、预算和节奏的路线。

重点渠道是微信、支付宝、小红书、抖音、高德和国内 OTA。

### 入境用户看到的价值

> 不熟悉中国的 App、语言和支付方式，也能得到真正可以执行的本地旅行方案。

重点是 Google/Apple 登录、中英双语、外宾住宿、证件、手机号、支付、点餐和导航衔接。

产品能力同时覆盖两类用户，但每一个推广页面、渠道活动和首次体验只能讲一个清楚的价值，不把两套文案混在一起。

## 明确保留，但不做成重型平台

| 能力 | 保留方式 | 暂时不做什么 |
| --- | --- | --- |
| 全平台 | 一套旅行服务，多端适配；桌面规划、移动执行、小程序轻入口 | 不在每个平台复制旅行逻辑，不同时开发五套独立设计系统 |
| 微信/支付宝/Google/Apple 登录 | 用于跨端继续、分享和保存；根据用户所在入口优先展示 | 不让登录挡住第一次体验，不建设复杂账号社交体系 |
| MCP 与可复用接口 | 作为其他 Agent 调用和低成本分发入口 | 不把 MCP 独立包装成另一套旅行产品 |
| 小红书/抖音/微信 | 用于发现线索、用户链接导入和受限只读研究 | 不做内容 Feed，不依赖未经授权的大规模抓取 |
| 飞猪/途牛等 OTA | 提供价格、库存和预订跳转 | 不重建完整 OTA 搜索、支付、订单和售后 |
| 高德 | 提供中国地点、路线、地图和导航衔接 | 不重做导航，不把非实时设施说成实时状态 |
| 到访反馈 | 形成下一位旅行者可用的决策数据 | 不做点赞排行、关注关系和创作者社区 |

## 下一迭代优先顺序

### 第一优先：让一次真实规划更快完成

- 从一句话或一组分享链接开始。
- 默认生成一份主方案和少量关键取舍。
- 即使部分数据源暂时不可用，也返回其他已经核实的领域，不让一个 Provider 阻断整趟旅行。
- 用户可以通过对话、选择器和地图自然调整同一份方案。

### 第二优先：补强中国在地发现

- 打通社交分享链接导入。
- 建立少量高质量、可追溯的目的地资料作为基础。
- 把“当地特色、为什么适合、路线代价、排队预约、入境摩擦”做成每个候选的固定判断。
- 在授权、安全和账号稳定后，再逐步加入小红书和抖音只读搜索。

### 第三优先：打通跨端连续体验

- 用户可以先试用，再在保存或跨端时登录。
- 同一账号在 Web、App、小程序中看到同一趟旅行。
- 桌面端负责比较，移动端负责执行，不机械复制同一排版。
- MCP 返回同一趟旅行的链接或标识，让用户可以回到可视化页面继续。

### 第四优先：建立行中和行后闭环

- 天气、延误、闭店触发局部调整。
- 旅途中提供“现在、下一步、备选”。
- 行后用短反馈补充真实花费、等待、适配人群和事实变化。

## 如何判断这次迭代是否值得

不要用生成了多少行程、调用了多少 Provider 或增加了多少 Skill 来证明成功。更有意义的是：

| 观察问题 | 建议指标 |
| --- | --- |
| 用户多久第一次感到有帮助？ | 从开始描述到出现可信主方案的时间 |
| Agent 是否真的替用户减少选择？ | 主方案确认率、平均需要比较的关键选择数量 |
| 推荐是否适合这次旅行？ | 候选接受率、用户要求整套重来的比例 |
| 地图是否帮助决策？ | 地图定位、路线比较后改变选择的比例 |
| 国内内容渠道是否形成差异？ | 由社交线索发现、经核验后进入行程的地点比例 |
| 全平台是否产生价值？ | 跨设备继续同一趟旅行的比例，而不是安装包数量 |
| 是否带来执行行为？ | 保存、分享、导航和预订跳转的比例 |
| 用户旅行时还会回来吗？ | 行中打开、临时调整和备选采用率 |
| 反馈是否真的帮助下一位用户？ | 有结构化反馈的地点，其后续接受率和纠错率 |

建议把最重要的产品指标定义为：

> **可执行方案完成率：用户确认了一份地图动线合理的旅行方案，并完成至少一个保存、分享、导航或预订跳转动作。**

## 最终判断

全平台、四类登录、MCP、小红书、抖音和微信都应保留。它们不是无意义的堆砌，前提是各自只承担清晰职责：

- 全平台负责在不同旅行场景中持续使用；
- 登录负责保存和跨端连续；
- MCP 负责进入其他 Agent 生态；
- 社交内容负责发现长尾线索；
- 高德和 OTA 负责核实位置、路线、库存和执行；
- Travel Agent 只拥有最重要的一层：**替这位用户把信息变成适合他的决定。**

下一迭代不应删除这些能力，而应围绕这一层重新收拢界面、数据接入和开发优先级。
