# 可见旅行规划工作台与多点路线真实用户 QA

> 日期：2026-08-27
> 范围：自然语言需求 → 吃住行玩候选 → 不落盘试选 → 多点路线与时间/预算/天气影响 → 确认 → 单域替换。
> 证据边界：本文区分 Provider 实际调用、应用组合链、浏览器用户路径与仍未验证的生产授权；动态班次与价格只记录本次 `checkedAt` 快照。

## 结论

此前“地图可用、候选在抽屉里比较”的设计没有回答普通旅行者最直接的问题：有哪些机票、酒店、游玩和餐饮可以选；选了以后整趟路线、时间、预算、步行、换乘和天气注意事项怎样变化。当前产品合同改为：

`看候选 → 加入试排 → 立即看到完整多点路线与影响 → 快捷替换 → 用户确认后才写入 TripState`

吃、住、行、玩仍是同一 TripState 上的四条任务链，没有拆成四个 Workflow。新增的是现有服务边界内的只读 `trip-mobility-preview-v1`，不是第二套旅行状态或新平台。

## 用户可见产品合同

1. Trip 工作区直接显示行、住、玩、吃四段选择流程，不再要求用户先打开候选抽屉才知道有哪些选项。
2. 每类同时显示已确认项和最多三个可比较候选；机票显示起终机场、班次、时间、本次票价与核验时点，酒店/地点显示实景图、位置、评分、参考价和来源。
3. 未确认领域默认选取首个候选形成“试排”，并明确标为未确认；点击其他候选只更新试排，不修改 TripState。
4. 地图和时间轴使用同一组试选节点。多日路线按日期回到住宿锚点，例如：`机场 → 酒店 → 晚餐 → 酒店 → 次日体验 → 酒店`，不再把跨日地点伪装成连续移动。
5. 每次试选同时回显路线总时间、单段步行、换乘、交通估价、候选参考价、总预算、同行人体力阈值和天气对四域的影响。
6. 推荐方式没有可绘制折线时，地图可使用同一路段由高德返回的其他交通方式折线作灰色虚线对照，并明确说明“具体方式以时间轴为准”；不画虚构直线。
7. 任一试选地点未成功定位时，路线显示具体缺失地点、禁用确认，并提供“重算路线”；不得静默从路线中丢掉该选项。
8. 确认后未选候选继续保留为“试试替换”。替换只拒绝同领域旧选项并选中新选项；其他已确认领域不变。前一个选择继续作为可恢复候选，允许再次切回。
9. 购买、预订和支付边界不变。确认候选只是旅行决策，不会创建订单。

## 真实浏览器路径

自然语言输入：2026-08-27 至 29 日，三人广州飞上海，浦东 T2，预算 ¥8,000；父亲单段步行不超过 600 米并尽量避开楼梯；住宿人民广场/南京东路；外滩、上海市历史博物馆、本地菜和不太大众的小店；先给候选，不替用户确认。

本次浏览器返回：

- 行：1 个航班候选；
- 住：3 个候选；
- 玩：3 个候选；
- 吃：3 个候选；
- 天气：上海旅行日期三天均为小雨提示，四域指导可见；
- 设施：地点详情区分“本次需要 / 当前取得 / 到场前确认”，不把入口、电梯、卫生间等地图记录写成实时运行状态。

动态库存示例仅代表本次查询：HU7431、飞猪参考价 ¥600，页面显示核验时间；它不是持续有效班次或固定价格。该班次到达时间与用户输入 14:00 不一致，页面明确标记为库存对照。后续 Research Criteria 只在 `arrivalConfirmed=true` 时把用户到达事实作为权威路线锚点；普通期望时间不会覆盖库存班次的实际到达点和时间。

### 试选未提交

第一次试排约为 136 分钟、973 米步行、交通估价 ¥221。将餐厅替换为“上海1号私藏菜”后，试排变为约 87 分钟、367 米步行、¥235；再把体验换成外滩后，变为约 88 分钟、267 米步行、¥235。

此时文件中的 TripState 仍为 revision 1、0 个 selected node、Mobility 未持久化、10 个待确认候选，证明浏览器比较没有暗中提交。

### 确认与单域替换

确认四个试选项后，行、住、玩、吃全部进入 selected，Mobility 按日期形成 5 段移动。随后只试选并确认“一间森林酒店(上海人民广场店)”：

- 机场、餐饮、体验保持原选择；
- 住宿从全季酒店替换为一间森林酒店；
- 试选阶段显示相对已确认路线约减少 77 分钟、570 米步行和 ¥4 交通估价；
- 确认后的实际状态为 revision 5、四域各一个 selected node、旧住宿为 rejected；
- residual proposal 仍保留 1 个住宿、2 个游玩和 2 个餐饮替代项；
- 持久化 Mobility 为 5 段：浦东机场 T2 → 一间森林酒店 → 餐厅 → 一间森林酒店 → 上海市历史博物馆 → 一间森林酒店。

### 移动端

390×844 视口真实渲染中，`documentElement.scrollWidth === clientWidth === 390`，没有页面级横向溢出。移动端保留 Chat / Trip / Map 三入口；Trip 使用横向候选卡，Map 显示 Today、当前航班、下一站酒店、5 段路线、非实时说明和变化恢复入口。

## 技术落地

- `TravelService.previewTripMobility`：基于当前 revision、已确认节点和本次 tentative selections 调用真实 Mobility Provider，返回路线与影响但不保存。
- HTTP：`POST /api/trips/:tripId/mobility/preview`；继续执行成员权限检查。
- Runtime partial selection：确认某领域后保留未选候选；替换时只修改同领域 selected node，并保存可恢复的前一选择。
- Amap Mobility：路线按 planning window 分日，住宿成为每日出发/返回锚点；每一段使用对应日期/时段查询，而不是复用 Brief 中第一个时间。
- Web：可见 Planning Workbench、候选横向轨道、多点地图、路线时间轴、预算/体力/天气影响、未定位 fail-closed 和确认条。
- Leaflet：去掉快速重绘时会触发 `clearRect` 异常的 Canvas 偏好，改用稳定 SVG 路径；蓝色实线与灰色对照虚线语义分开。
- 等待体验：从静态“20–60 秒”改为按阶段说明理解、并行检索、路线组合和实时来源较慢，不再在超时后让用户误以为页面卡死。

## 验证层级

| 层级 | 本轮证据 | 不能替代什么 |
| --- | --- | --- |
| Provider | 高德地点/天气/路线真实调用；飞猪、途牛库存 smoke | 商业授权、长期稳定性和用户路径 |
| 应用组合链 | Research Criteria、角色融合、试排 Mobility、partial replacement 合同 | 浏览器可理解性 |
| 浏览器用户路径 | 自然语言创建、候选可见、两次试选变化、确认、酒店替换、桌面与 390px 移动 QA | iOS/Android/微信/支付宝真机与生产部署 |
| 状态证据 | 比较前 TripState 不变；确认/替换后 selected、rejected、residual proposal 与 Mobility 一致 | 实际购买、入住、现场设施运行状态 |

## 仍未关闭

- 当前实时来源在复杂四域检索和五段路线中可能需要约 40–120 秒；阶段反馈已改善，但后续仍应通过 Provider 缓存、并发预算和增量返回缩短首个可用结果时间。
- 当前候选池在严格机场/航站楼/日期过滤后可能只有一个可验证航班；不能为满足卡片数量而放宽成无关机场或生成假库存。
- “小众、当地人知道”仍主要依赖地图实体与用户到访闭环；缺少已授权社交检索时必须标记证据不足。
- 互动底图生产授权、真实 OAuth、OTA 商业授权、外宾住宿资格、实时设施、各端真机和完整英文地点归一仍是上线门。
- 候选参考价可能是起价、单晚价或单人票价；当前只用于比较，不是整趟结算总价。
