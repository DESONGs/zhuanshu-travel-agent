# 界面与路线执行信息

## 设计方向

产品先采用对话优先的信息结构：大屏中间是旅行编辑对话，右侧是 Agent 返回的方案画布，左侧只保留可恢复的旅行对话；移动端先显示对话，再垂直显示同一份方案画布。Map Pulse 作为旅行执行阶段的交通与地图详情语言，而不是让用户先编辑时间线的首页。它借鉴 Airbnb 的温和、宽松、目的地优先节奏，但不复刻 Airbnb 的房源列表或版式。

选定移动端视觉源位于 `design/reference/map-pulse-mobile.png`。地点研究可用时，方案画布展示候选照片和由服务端生成的高德静态地图，Key 不进入浏览器；确认后继续显示已选地点照片与导航跳转。当前 UI 的唯一事实仍来自真实检索或用户确认：地图资料未接线时，界面明确说明暂时无法取得地点，不用固定城市、坐标、库存或设施填充画面。

天气是方案画布的第一项环境信息，位于旅行摘要之后、吃住行玩候选之前。桌面和移动端都显示预报覆盖了哪些旅行日期、主要风险、对四域的具体影响和来源核验时间；恶劣天气下，经过来源确认的室内体验优先，户外项目标记“天气需备选”。没有对应日期预报时只显示重新核验时机，不用当前天气填充。

旅行摘要之后增加“同行人的安排重点”：总预算和整体节奏先回显，再按人显示步行、换乘、台阶、休息、时间与设施要求。这里使用“需要少走路”“单段步行≤800米”等尊重且可执行的语言，不显示诊断；没有分别记录时直接提示用户可以继续补充，而不是假装 Agent 已经理解。

## 城市移动与路线详情合同

`trip-mobility-v1` 是方案层的城市移动合同：每一段包含起终点、建议方式、步行/公交地铁/打车备选、查询时估算耗时、步行量、换乘、估价、路线折线、来源、核验时间和有效期。步行步骤同时保留高德 `walk_type`，并把扶梯、直梯、阶梯、斜坡归一为可展示的路线设施参考。用户确认地点后由 Runtime 自动刷新；地点或范围变化后旧路线变为待刷新。前端只说“查询时路线估算”，不说“实时到站”或“即时车费”。

路线设施参考统一标记为“地图路线资料、非实时、建议现场确认”。出现阶梯时，`avoidStairs` 或 `stepFreeRequired` 对应的同行人会触发硬冲突并优先改选打车或无明确阶梯的路线；出现直梯或斜坡只能作为有帮助的部分证据，不能证明当前正在运行，也不能单独证明起终点之间连续无障碍。没有明确步行上限时，Adapter 可以内部采用保守排序目标，但不得把这个目标回显成用户自己设定的上限。

`transit-segment-v1` 保留为更深的站内执行合同：

`transit-segment-v1` 将一段交通拆成步行、进站、乘车、换乘、出站和抵达步骤。每项设施具有 `kind`、区域、可用状态、来源、核验时间和有效期：

| 类别 | 可展示区域 |
| --- | --- |
| 电梯 / 无障碍卫生间 | 站外、非付费区、付费区、站台层 |
| 卫生间 | 非付费区、付费区、站台层 |
| 寄存柜 / 充电宝 / 母婴室 | 站外、非付费区、付费区、站台层 |

来源为 `user_input` 的信息显示“待核验”。高德 POI 的入口、出口和室内地图，以及路线 `walk_type` 的直梯、扶梯、阶梯、斜坡，只能显示“地图有记录、非实时、现场确认”；只有获授权的实时来源明确给出运行状态且仍在 `freshUntil` 内时才显示“当前可用”。“开始导航”在路线来源未接线时禁用，不能引导用户进入虚假导航。

## 产品状态

1. 初始对话：用户从一句自然语言需求开始；信息不足时 Agent 只追问一个关键约束。
2. 旅行草案：Agent 已理解基础范围后建立共享状态；方案画布先显示天气核验状态，再显示吃住行玩覆盖，不能把空草案伪装成已规划行程。
3. 待确认提案：Skill 返回的信息只在 revision/write contract 校验后出现；用户可明确接受或拒绝。
4. 已确认地点：Mobility Gate 自动生成 `trip-mobility-v1`，路线卡和静态地图读取同一观察；路线不完整时 QA 明确阻止“完整行程”表述。
5. 行中交通：取得获授权的站内设施或实时到站来源后，再把选定公共交通方案下钻为 `transit-segment-v1`；当前不得显示为已接线。
6. Provider 未接线：保留已确认的结构和用户信息，显示影响与恢复条件；不自行补全动态路线、实时到站、入口或设施。此前已经取得且来源明确的非实时设施记录可以保留，但必须显示其时间和非实时性质。
7. 失效或中断：保留无关锁定决定，将受影响节点放入 dirty set，要求重新核验或生成局部重排提案。
