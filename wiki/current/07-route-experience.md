# 界面与路线执行信息

## 设计方向

产品采用 Agent 优先、地图主导决策的信息结构：免登录首屏从文字、语音、图片或链接意图开始；第一结果先给准备清单、全局地图、最多三个关键取舍和一个下一步，不先铺满四域卡片。大屏保留可恢复、可折叠和可调整宽度的旅行对话，右侧结果区在窄容器时自动改单列；用户保存的旧栏宽不得裁切准备卡和地图结果。详细候选只在用户点击比较时展开。移动端固定 Chat / Trip / Map 三入口，Map 在已确认地点后显示 Today。Map Pulse 贯穿“发现地点—比较取舍—确认路线—行中执行”，但开发底图只用于位置比较，正式导航仍回到高德。

选定视觉源包括 `design/reference/map-pulse-mobile.png` 与本地米其林食图的列表—地图交互。地点研究可用时，开发环境用 Leaflet 展示真实坐标和路线折线；高德 GCJ-02 坐标只在渲染层转换为 Web 底图坐标，不改写旅行状态，正式导航继续跳转高德。生产若未配置合规互动底图，则回退到服务端生成的高德静态地图；Key 不进入浏览器。当前 UI 的唯一事实仍来自真实检索或用户确认：地图资料未接线时明确说明不可用，不用固定城市、坐标、库存或设施填充画面。

候选与地图采用双向焦点：列表选择更新地图标记，地图标记也更新当前候选；已选行程同样以一张地图展示地点和已核验路线。地图旁只显示可追溯的“判断依据”和“待补证据”，例如位置已定位、具名来源已核验、设施地图参考、结构化到访反馈、外宾资格、排队时间待补。用户点“更在地、少绕路、少排队、入境友好”时回到对话补充要求，由 Parent Agent 重新比较，不在浏览器里用隐藏规则替用户决定。

天气是方案画布的第一项环境信息，位于旅行摘要之后、吃住行玩候选之前。桌面和移动端都显示预报覆盖了哪些旅行日期、主要风险、对四域的具体影响和来源核验时间；恶劣天气下，经过来源确认的室内体验优先，户外项目标记“天气需备选”。没有对应日期预报时只显示重新核验时机，不用当前天气填充。

旅行摘要之后增加“同行人的安排重点”：总预算和整体节奏先回显，再按人显示步行、换乘、台阶、休息、时间与设施要求。这里使用“需要少走路”“单段步行≤800米”等尊重且可执行的语言，不显示诊断；没有分别记录时直接提示用户可以继续补充，而不是假装 Agent 已经理解。

## Agent-assisted Trip Workspace

桌面 Trip 视图采用一个工作区，而不是连续卡片页面：

- `Trips drawer`：承载历史旅行与会话，默认收起；
- `Agent Rail`：约 340px，可折叠，只显示当前决策附近的对话；
- `Trip Surface`：路线骨架或 Day Timeline；
- `Map Surface`：稳定占主工作区 40%—45%，与日期、地点、路线段共享焦点；
- `Candidate Drawer`：只在比较或变化提案时打开，读取 pending proposal；
- `Trip Kit`：确认后按需展示票据、预订、准备、预算、打包与分享。

Readiness、天气和下一步不再分别占据多张首屏卡片。默认只显示一条有来源的阻塞摘要；用户展开时，才看到每项原因、来源、状态和动作。

### 四种可见状态

| 状态 | 用户看见什么 | 数据所有者 |
| --- | --- | --- |
| 候选 | Agent 核验后等待比较的地点，不在日程中 | `pendingProposals[].byDomain` |
| 路线骨架 | 已选地点与空间关系，时间和部分移动仍未完成 | Decision Graph + Mobility Observation |
| Day Timeline | 日期、时间窗、顺序、移动和同行人约束可以成立 | 后续 `DayPlanProposal` |
| 已确认/已预订 | 用户确认、履约记录或锁定项 | Fulfillment Plane + locks |

用户拖动地点、跨日移动或调整时间时，界面先产生 Change Preview。Change Preview 至少显示新增/移除/换序、预算变化、步行/换乘、受影响同行人、锁定项和待核验信息；它只能提交为 Proposal，不能绕过 Parent Agent。

## 城市移动与路线详情合同

`trip-mobility-v1` 是方案层的城市移动合同：每一段包含起终点、建议方式、步行/公交地铁/打车备选、查询时估算耗时、步行量、换乘、估价、路线折线、来源、核验时间和有效期。步行步骤同时保留高德 `walk_type`，并把扶梯、直梯、阶梯、斜坡归一为可展示的路线设施参考。用户确认地点后由 Runtime 自动刷新；地点或范围变化后旧路线变为待刷新。前端只说“查询时路线估算”，不说“实时到站”或“即时车费”。

路线设施参考统一标记为“地图路线资料、非实时、建议现场确认”。出现阶梯时，`avoidStairs` 或 `stepFreeRequired` 对应的同行人会触发硬冲突并优先改选打车或无明确阶梯的路线；出现直梯或斜坡只能作为有帮助的部分证据，不能证明当前正在运行，也不能单独证明起终点之间连续无障碍。没有明确步行上限时，Adapter 可以内部采用保守排序目标，但不得把这个目标回显成用户自己设定的上限。

`transit-segment-v1` 保留为更深的站内执行合同：

`transit-segment-v1` 将一段交通拆成步行、进站、乘车、换乘、出站和抵达步骤。每项设施具有 `kind`、区域、可用状态、来源、核验时间和有效期：

| 类别 | 可展示区域 |
| --- | --- |
| 电梯 / 无障碍卫生间 | 站外、非付费区、付费区、站台层 |
| 卫生间 | 非付费区、付费区、站台层 |
| 寄存柜 / 充电宝 / 母婴室 | 站外、非付费区、付费区、站台层 |

来源为 `user_input` 的信息显示“待核验”。高德 POI 的入口、出口和室内地图，以及路线 `walk_type` 的直梯、扶梯、阶梯、斜坡，只能显示“地图有记录、非实时、现场确认”；只有获授权的实时来源明确给出运行状态且仍在 `freshUntil` 内时才显示“当前可用”。“开始导航”在路线来源未接线时禁用，不能引导用户进入虚假导航。

## 产品状态

1. Guest 初始对话：自动创建临时会话，用户从一句自然语言需求开始；信息不足时 Agent 只追问一个关键约束。
2. 第一份结果：回显旅行理解、准备缺口、地图路线骨架、最多三个取舍和下一步；真实来源缺失时显示 partial，不等待也不伪造四域完整。
3. 待确认提案：Skill 返回的信息只在 revision/write contract 校验后出现；用户可明确接受或拒绝。Readiness 更新使用独立版本，不能意外废弃待确认方案。
4. 已确认地点：Mobility Gate 自动生成 `trip-mobility-v1`，路线卡和地图读取同一观察；路线不完整时 QA 明确阻止“完整行程”表述。
5. Today：从 TripState 派生当前/下一步、路线、准备缺口和变化入口；没有可靠时间时显示 `needs_schedule`，不能冒充实时行中日程。
6. 行中交通：取得获授权的站内设施或实时到站来源后，再把选定公共交通方案下钻为 `transit-segment-v1`；当前不得显示为已接线。
7. Provider 未接线：保留已确认的结构和用户信息，显示影响与恢复条件；不自行补全动态路线、实时到站、入口或设施。此前已经取得且来源明确的非实时设施记录可以保留，但必须显示其时间和非实时性质。
8. 失效或中断：保留无关锁定决定，将受影响节点放入 dirty set，要求重新核验或生成局部重排提案。
9. 候选池与日程：pending candidate、路线骨架和 Day Timeline 使用不同视觉状态；不能因为地点被选中就显示伪精确时间。
10. 离线 Today：仅缓存已确认的最小执行快照；过期、路线未核验或设施非实时必须继续可见。

## 地点详情与到访反馈

吃、住、玩的地点详情按需展开照片、地图、设施、来源与到访者汇总，不在方案概览中铺开全部信息。未确认的候选可以阅读已有汇总；只有已经加入本次旅行的地点才显示“我去过，留一条到访记录”。

到访记录支持“体验感受”和“现场信息有变化”两类。体验感受通过推荐倾向、有限标签、可选花费/等待形成匿名结构化汇总；自由文字不跨旅行公开。现场变化只增加待核验提示，直到官方、运营方或独立来源完成核验前，不改变营业、价格、设施等地点事实。取消匿名分享时，记录只留在当前旅行。
