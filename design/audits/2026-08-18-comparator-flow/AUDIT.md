# Travel Agent 对照产品交互审计

日期：2026-08-18

## 审计范围

- 参考 Demo：`https://lvxu-travel-2026.bobox77769.chatgpt.site/`
- 当前产品：本地真实 Web 入口、一次自然语言生成方案、桌面与移动端方案查看
- 用户目标：不学习复杂产品，也能用文字、语音或少量按钮讲清需求，获得可比较、可确认、可继续修改的真实旅行方案

本次只把参考 Demo 当作交互样例。它明确包含演示房态，页面中的班次、价格、新鲜度和“已核验”不能作为真实 Provider 证据。

## 总结

当前产品方向没有错：它已经真实实现了“先对话、再研究、最后确认”，并在本次测试中由 V4 Flash 返回了自然语言答复，由飞猪 AI 开放平台和途牛官方 MCP 返回了大理景点、酒店图片与跳转链接。真正的短板是交互没有把 Agent 的理解、开放决定和方案变化变成连续可操作的界面：用户先读一大段文本，再去另一个长画布自己寻找应该做什么。

参考 Demo 最值得借鉴的不是视觉，而是四件事：先分流用户意图、把已知约束变成可见控件、一次只比较一个有意义的取舍、最终把预算/日程/锁定/优化放进同一张旅行总览。不能照搬的是长表单、固定三步购物流程、静态演示数据和“全部已核验”的过度承诺。

## 流程步骤与健康度

| 步骤 | 观察 | 健康度 |
| --- | --- | --- |
| 1. 进入产品 | 参考 Demo 用“已知目的地 / 随机探险”降低起步焦虑；当前产品有清晰 Chat-first 文案，但登录后立刻出现空对话列表、空画布和模型选择器。 | 当前可用，起步仍有认知负担 |
| 2. 表达需求 | 当前产品支持一句自然语言并能真实理解；参考 Demo 只支持表单和按钮，没有自然语言或语音。 | 当前产品更正确，但缺少辅助输入 |
| 3. 补齐约束 | 参考 Demo 用同行人、节奏、预算和步行量按钮快速收敛；当前产品把追问埋在长回复末尾，用户只能再次打字。 | 需要重点优化 |
| 4. 等待研究 | 当前产品约 30 秒返回结果，只有通用等待提示；方案画布在完成前几乎没有渐进反馈。 | 功能可用，等待体验弱 |
| 5. 比较方案 | 参考 Demo 把交通、体验和酒店分别做成清晰比较卡；当前产品一次展示四域和大量原始描述，用户需要自己找决策重点。 | 信息真实，决策负担偏高 |
| 6. 形成行程 | 参考 Demo 的预算总览、按天时间线、锁定和一键优化很直观；当前产品先返回候选，地图和按天编排不在首屏价值时刻。 | 当前尚未形成足够强的完成感 |
| 7. 移动端继续修改 | 参考 Demo 有底部固定动作，但表单和双列卡片过密；当前产品用“查看方案”在对话与画布间跳转，但长文本占满首屏。 | 两者都需融合改进 |

## 值得保留

### 当前产品

- 对话是唯一主入口，不要求用户先做行程。
- 真实 Provider 不可用时不造假；候选有图片、来源、时间和 OTA 跳转。
- 同行人按人保存，预算、体力、天气和四域在同一旅行状态中。
- 变更需要用户确认，底层边界比参考 Demo 更适合真实产品。

### 参考 Demo

- “已知目的地 / 随机探险”是对新手友好的意图分流。
- 交通卡同时显示门到门时间、价格、为什么推荐和来源新鲜度。
- 体验选择把图片、路线、适配理由、官方资料与用户经验放在同一决策上下文中。
- 酒店比较强调“住在哪里会让每天少绕多少路”，而不是只比较房间属性。
- 最终页把吃、住、行、玩、预算、每天步数、锁定和局部优化合并成一个旅行对象。

## 主要问题

### 当前产品

1. 首次进入工作区时同时出现空对话列表、空画布和输入区，真正的主动作不够集中。
2. Agent 的第一轮回复过长。用户需要的其实是“我理解了什么、找到了什么、现在只差哪一个决定”。
3. 追问没有快捷答案。预算、出发地、住宿位置、节奏等高频问题都要求用户重新输入。
4. 已理解信息不可见、不可点改。用户无法快速确认“国庆 5 天 / 3 人 / 轻松 / 预算待定”。
5. 普通用户看到了 `V4 Flash`、`Kimi K3` 和“途牛官方 MCP”等技术选择；这些应下沉到设置或来源详情。
6. 方案画布优先展示状态卡和长候选描述，地图、按天时间线和关键取舍出现得太晚。
7. 移动端的助手回复是一整屏文字；“查看方案”能跳转，但没有形成可随时切换的工作节奏。
8. “不需要爬坡赶路”等适配结论必须由路线或设施证据支撑，不能只根据景点简介生成。

### 参考 Demo

1. 用户必须先选分支并填写长表单，无法直接说一句完整需求。
2. 吃、住、行、玩被包装成连续购物步骤，容易弱化它们之间的动态影响。
3. 移动端仍保留双列卡片和长表单，文字与点击目标偏小。
4. “长按编辑”、无文本的图标按钮和依赖视觉位置的流程，对键盘和辅助技术不友好。
5. 演示房态、固定核验分钟数、错误币种和“全部关键信息已核验”不适合真实产品。

## 建议的统一黄金路径

1. **一句话开始**：登录后直接聚焦文字输入，旁边提供语音按钮；下方只保留 3 个轻量起步选项，例如“我有目的地”“帮我找地方”“导入已有想法”。
2. **立刻回显旅行摘要**：首句解析后，在对话顶部出现可编辑 chips，例如 `广州出发`、`大理`、`国庆 5 天`、`3 人`、`轻松`、`预算待定`。缺失项可点补充，不阻塞可先做的研究。
3. **一次只问一个关键问题**：问题下方直接给 2–4 个答案按钮和“我自己说”。例如住宿预算给“<¥500 / ¥500–900 / 位置优先 / 自己输入”。
4. **边研究边出现**：等待时，方案区显示用户可理解的进度，如“正在比较少走路的住宿位置”“正在把景点与餐厅排在同一条路线上”，而不是 Provider 或 Runtime 名称。
5. **先给决策，不先给四栏**：第一批结果围绕真实取舍组织，例如“住古城附近还是大理站附近”，每个方案同时带出对餐饮、交通和体力的影响。
6. **确认后形成旅行总览**：桌面端保留对话 + 方案/地图并排；移动端使用同一状态的“对话 / 行程 / 地图”切换。默认先显示按天时间线、地图、预算和每天步行量，再按需展开来源。
7. **自然语言与 GUI 同时可改**：用户既可以说“第二天少走一点”，也可以点“少走路”“控制预算”“少换酒店”“雨天方案”。两种输入都生成同一种待确认变更，不维护两套产品状态。
8. **语音不自动提交**：按住或点击录音后先显示转写文本，允许编辑，再发送；始终提供键盘输入、清晰录音状态和权限失败恢复。

## 优先级

### 第一批：先解决流畅性

- 旅行摘要 chips 与缺失项提示。
- Agent 回复压缩成“理解 / 结果 / 一个问题”。
- 每个追问的快捷答案按钮。
- 生成过程的渐进式方案骨架。
- 隐藏模型名与 MCP 等工程术语。
- 移动端“对话 / 行程 / 地图”切换，避免整页向下找方案。

### 第二批：增强旅行完成感

- 按天时间线、地图与卡片选中联动。
- 以跨域取舍为单位的比较卡，而不是四域各选一个。
- 预算、步行量、换乘和同行人约束的总览。
- 锁定、局部调整、修改前后差异说明。
- 语音输入与转写确认。

### 第三批：探索与复用

- “帮我找地方”的探索式轻问答。
- 收藏、分享给同行、导入已有攻略。
- 行中模式的导航、设施和异常重排。

## 可访问性验证边界

本次确认了可见布局和 DOM 中的按钮、单选、标签结构；没有完成屏幕阅读器朗读顺序、全键盘操作、浏览器缩放、语音权限失败和真实移动设备触控测试，因此不能据此声称符合 WCAG 2.2 AA。
